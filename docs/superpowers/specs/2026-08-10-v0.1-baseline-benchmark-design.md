# v0.1 Baseline Benchmark Design

## Goal

Record a reproducible long-chain performance and numerical-sanity baseline for
the public `BMSPCov` and `SBMSPCov` estimators at source baseline `69e3535`.
The baseline supports optimization decisions and comparison with `bspcov`
1.0.3. It is not evidence of MCMC convergence or universal speedup.

This design supersedes and removes the earlier short-chain microbenchmark.

## Workload

- Dimensions: 25, 50, 100, and 200, with `n = 3p`.
- Estimators: BM and correlation-screened SBM.
- Backends: CPU and NVIDIA GPU on the same host.
- Precision: float32 and float64.
- Fixture: canonical float64 data with 5% target precision-matrix density and
  seed 20260803. Each execution casts the same data to its requested dtype.
- MCMC work per chain: 50 burn-in sweeps and 50 retained samples.
- Chains: four per measured repetition.
- Repetitions: ten independently keyed measured repetitions per cell.
- Compilation: one synchronized compile-plus-execution fit per cell, recorded
  separately and excluded from primary timing summaries.

Each repetition records normalized wall time, throughput, all raw chain or fit
times, retained draw count, posterior-mean validity, and truth-relative
Frobenius error. Repetition keys are deterministically derived from the base
seed without changing the shared fixture.

## Execution model

Run two independent lanes concurrently. Do not run multiple cells concurrently
inside either lane.

- The GPU is local to NUMA node 0. Pin the GPU process and its host memory to
  node 0. Each repetition runs four fresh single-chain fits sequentially and
  uses their arithmetic mean as normalized wall time per chain.
- Pin the Python CPU process and its memory to NUMA node 1. Each repetition
  runs one vmapped four-chain fit and divides its synchronized total wall time
  by four.
- Run R on the CPU lane after the Python CPU cells, overlapping it with the
  remaining GPU lane when possible. Pin it to NUMA node 1.
- Record the exact CPU lists, NUMA policy, thread environment, process model,
  and lane start/end times. If affinity cannot be applied, fail rather than
  silently producing incomparable records.

This schedule reduces total wall time without mixing CPU and GPU host work on
the same socket. It intentionally measures one cell at a time per resource
lane so memory-bandwidth contention between benchmark cells cannot distort the
distribution.

## Python runner and records

Replace the existing warmed-repetition behavior in
`benchmarks/sbm_public_scaling.py` with the four-chain execution model above.
Keep one JSONL file per estimator, backend, and dtype, with one dimension
record per line. Every record contains ten raw repetition objects plus summary
statistics; no burn-in-1 or two-sample record remains in the curated baseline.

For every repetition, combine all 200 retained draws before checking that the
posterior mean is finite, symmetric, and positive definite. Preserve raw
repetition errors so accuracy variation can be plotted rather than inferred
from a single run.

## R comparison

Compare BM at `p=200`, `n=600` with an isolated installation of `bspcov`
1.0.3. R uses `nchain=4`, `do.parallel=TRUE`, 50 burn-in sweeps, 50 retained
samples, and ten repetitions on the same canonical fixture.

Normalize each R repetition as four-chain wall time divided by four. Record
worker startup inside the measured `bmspcov()` call because it is part of the
public R execution path. Reuse the already measured Python p=200 records when
assembling the R comparison; do not rerun Python solely for that report.

## Human-readable outputs

Replace the existing baseline report rather than preserving a microbenchmark
section. Include:

- median normalized wall time, interquartile range, and chains per second;
- R-relative and CPU/GPU speed ratios computed from repetition medians;
- truth-relative error distributions and output-validity checks;
- a wall-time boxplot with all ten raw points overlaid;
- an error boxplot with all ten raw points overlaid;
- exact workload, source revision, host topology, affinity, software versions,
  commands, and limitations.

Use boxplots with raw points instead of violin plots because ten observations
are too few for a stable kernel-density estimate. Store reproducible plot code
beside the benchmark runner and commit the rendered SVG files.

## Acceptance criteria

1. No curated result or report describes the removed burn-in-1, two-sample
   microbenchmark.
2. All 32 Python cells contain ten repetitions of four chains with 50 burn-in
   and 50 retained samples per chain.
3. CPU records use one vmapped four-chain fit per repetition; GPU records use
   four sequential single-chain fits per repetition.
4. Primary timing excludes compilation and uses the requested normalized
   per-chain formulas.
5. The R comparison contains ten `bspcov` 1.0.3 repetitions and reuses matching
   Python p=200 records without duplicate Python measurement.
6. Every repetition has 200 retained draws and a finite, symmetric,
   positive-definite posterior mean.
7. JSONL records, tables, and plot points agree exactly before rounding.
8. Focused benchmark tests and repository quality hooks pass; hardware runs do
   not become GitHub CI jobs.
